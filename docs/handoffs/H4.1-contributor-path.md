## Context in one paragraph

What makes this project work is less its code than its method. Every change to the extractor is measured on a
public corpus pinned by SHA, judged item by item at the source, and refused if precision drops anywhere. The hold-out
is never tuned on. A refactor must leave the corpus identical. A number is only quoted with the run that produced
it. Someone who arrives with an AI and none of that context will do what an AI does by default: add a heuristic
until the example passes, call a green test a success, trade precision for recall, edit the expected list to match
the output, or quote a number nobody measured. H4.1 makes the method the easiest path for that person and their AI:
it is written where they read first, every claim it asks for can be checked by a command, and the checks that can
run in CI do.

## Who this is for

- **The contributor:** a developer who found the project on GitHub, cloned it, and works with an AI agent (Claude
  Code, Cursor, Copilot, Codex, Aider…). They may never talk to the author before the first PR.
- **Their AI:** a fresh session that reads `AGENTS.md`, follows links, runs commands, and writes code. It has no
  memory of this project's history, and it will fill any gap in the docs with a plausible guess.
- **The reviewer:** the author, or a maintainer, who needs the PR to carry its own evidence.

## What has to transfer

Each part of the method, what it means in practice, where it is written today, and what checks it:

| # | Part of the method | In practice | Written today in | Checked by |
|---|---|---|---|---|
| 1 | **Measured, not felt** | Every claim about the extractor is a number from a run that anyone can repeat, with the run's name and date | `corpus-report.md` | the PR quotes the command and its output |
| 2 | **The cycle of a change** | A fixture case that fails without the rule → the corpus against the baseline → every diff item judged at its source line → the expected lists → a new baseline | guide §5 | the PR's test plan |
| 3 | **Precision before recall** (H2-D11) | A rule that raises recall and drops precision in any repo does not go in | `decisions.md` | the per-repo report |
| 4 | **The expected list is evidence, not output** (H2-D4, D15) | It comes from a committed spec checked against the code, or from reading files within a scope fixed first; never from the extractor's output. Every edit cites `file:line` | `corpus_metrics.py` docstring | review of the expected-list diff |
| 5 | **The hold-out is never tuned on** (H2-D20) | Its expected lists are committed before the extractor first runs on it; no rule is written for it; a hold-out repo that gets worked on becomes corpus | `decisions.md`, corpus report | the order of commits; review |
| 6 | **A refactor changes nothing** | The corpus and the hold-out give `0 repo(s) differ`; a difference is a defect of the refactor, not a gain | H5 | the corpus diff |
| 7 | **Statistics** | Timings are medians of at least 3 runs alone on the machine, with their range; the sample size is always stated; the corpus varies ~28 % between runs, so small effects use a microbenchmark | H6, "How it is measured" | the numbers' table in the PR |
| 8 | **Deterministic, no LLM as parser** | The same commit gives the same graph. Where a decision needs a type not declared in sight, the answer is `needs-resolver`, not a guess. A limitation is recorded, not estimated | ADR-002 | the fixtures; review |
| 9 | **One cause per commit** | A rule, a refactor and an expected-list correction never share a commit, so that "0 differ" and a judged diff keep meaning something | H5 pitfalls | review |
| 10 | **Validated where it runs** | A change headed for `main` is also checked on a live install: a dry-run of `main` against the branch, pictures of the graph, the golden questions | `decisions.md` | the PR's test plan |
| 11 | **Code shape and hygiene** | Complexity ≤ 9, modules ≤ 300 lines, comments that say only why, no doc references and no project names in the code | ROADMAP principles | `shape.py` in CI; `test_code_hygiene.py` |
| 12 | **Privacy and safety** | No real tenant, client or private project name anywhere; corpus repos are third-party code that never runs outside the indexer's container | `AGENTS.md` | review; the hygiene test |

## How an AI contributor goes wrong, and what stops it

| Failure | How it looks | What stops it |
|---|---|---|
| A rule fitted to the example | The new case passes; elsewhere, routes appear that the code does not serve | The fixture's counterexample; the corpus diff judged item by item; precision per repo |
| A green test called success | "Tests pass, done" | The definition of done asks for the corpus run's name and the judged diff |
| The expected list edited to match the output | Recall goes up with no extractor change, or with one | Expected-list edits with `file:line` evidence, in their own commit; `CODEOWNERS` on `indexer/tests/corpus_expected/` |
| A number nobody measured | "This makes indexing 3× faster" | The rule "no number without the command that produced it"; the PR template |
| Code that is not there | Calls to functions, flags or files invented from the docs | "Read the file before citing it" in `AGENTS.md`; a CI check that every repo path the docs name exists |
| A guess where a type is needed | A heuristic on names to pick a receiver's type | Rule 8; the guide's "where the extractor stops" |
| Tuning on the hold-out | A rule that fixes a hold-out miss | Rule 5; a hold-out change outside a measurement point is flagged in review |
| Noise taken for an effect | One run with the corpus running alongside | Rule 7 |
| Refactor and rule in one commit | "Refactored and fixed a small thing" | Rule 9 |
| Known traps | `python -m` inside the image runs the image's code, not the mounted one; tree-sitter nodes compared by `is`; the order of `normalize_path`'s regexes | A "Pitfalls" section in the contributor guide, kept from the handoffs' |
| Docs that lag the code | The guide describes a function that moved | Docs changed in the same PR as the code; counts generated, not typed |

## What a contributor can do, and when it is done

| Contribution | Done when |
|---|---|
| **Report a miss or a wrong route/call** | The issue gives the repo and commit, the `file:line`, what the code serves or requests, what the graph shows, and the command that showed it (issue template) |
| **Teach the extractor a framework pattern** (a recognizer, after H5) | A fixture case and a counterexample that fail without the rule; the corpus against a baseline of `main`, every diff item judged at the source; no repo's precision drops; the expected lists updated in their own commit with evidence; the new baseline named in the PR |
| **Add a repo to the corpus** | Pinned by SHA; a license that allows reading it; an expected list from a spec checked against the code, or from files read end to end within a scope fixed first; a seeded sample judged at the source; no extractor change in the same PR |
| **Propose hold-out repos** | Their expected lists are committed before the extractor runs on them; the measurement is done once, by a maintainer, at a measurement point |
| **Add a language** | ADR-003's path: a module under `languages/<lang>/`, the grammar in the image, fixtures, corpus repos for it, the guide's table |
| **Refactor** | The corpus and the hold-out `0 repo(s) differ`; the time measured alone, no worse; one refactor per commit |
| **Change the MCP** | A golden question first, with its Cypher; `scripts/mcp-it.sh` green against an ephemeral Neo4j |
| **Change the docs** | Every number comes from a source that is linked; links and repo paths checked |

## What an outsider can run, and what they cannot

- **The tests:** `indexer/scripts/test.sh`, in the test image.
- **The corpus**, with 3.6 GB of clones and a Docker with 9 GiB for 3 containers at once (about 8 minutes). The
  baselines live in `~/.cache/aidd-corpus/runs`, on the author's machine, so an outsider has none. Their protocol
  today is to run `main` first, as their own baseline, then their branch against it:

  ```bash
  git switch main && indexer/scripts/corpus.sh --label main-$(git rev-parse --short HEAD)
  git switch my-branch && indexer/scripts/corpus.sh --baseline main-<sha>
  ```

  A baseline is about 8 MB for the 55 repos, so publishing it is cheap (decision H4.1-D1).
- **The hold-out:** its expected lists are public in the repo, so it is not blind to anyone who reads them. It
  holds because no rule is written for it (decision H4.1-D2).
- **A live install:** it needs a portfolio of real repos. An outsider can validate on a demo tenant made of public
  repos (decision H4.1-D4).

## How the knowledge reaches an AI

1. **`AGENTS.md`** stays the entry point. It gains a short "Contributing" section that names the method's twelve
   parts and links to the rest. It is the one file every agent tool reads.
2. **`CONTRIBUTING.md`** at the root, for people and agents alike: the cycle as a checklist, the definition of done
   of each contribution, the commit and PR conventions, what an outsider can run.
3. **Playbooks, one per contribution type** (`docs/en/guides/`, in H4's architecture): "Teach the extractor a
   pattern", "Add a corpus repo", "Measure with the corpus", "Refactor without changing behavior", "Change the MCP".
   Each one is a sequence of commands with what their output must show. They are tool-agnostic Markdown, so any agent
   follows them (decision H4.1-D3 on whether a Claude Code skill wraps them too).
4. **An explanation page, "Measured, not felt"** (`docs/en/explanation/`): why precision comes before recall, what
   the statistics are, how expected lists and the hold-out work. It is told through what happened, because a reason
   with a story behind it is harder to skip:
   - the first hold-out of 2026-10-17, which showed C# recall at 48.5 % and Go at 19.7 % on repos the rules had never
     seen, and why the hold-out exists;
   - the NodeBB precision that fell from 94 to 80 % with runtime prefixes, and why a rule that drops precision does
     not go in;
   - PR #5's increment 12: two defects that only a live install showed, and why validation does not stop at the
     corpus.
5. **A PR template** whose test plan asks for the evidence itself: the commands, the run names, the judged diff, the
   numbers with their `n` and spread. **Issue templates** for a miss, a wrong item, a framework request.
6. **Checks in CI**, so that the method does not depend on anyone reading it:
   - the tests, the code hygiene test and the shape report (they exist);
   - links and every repo path named in the docs exist;
   - a PR that touches both the extractor and `corpus_expected/` gets flagged for review;
   - the corpus on GitHub's runners, triggered by a label, posting the diff against `main` and the per-language P/R
     as a comment (decision H4.1-D5). A public repo's runners are free, and that would make the measurement a service
     instead of a local chore.

## The acceptance test: re-enact past work with a fresh agent

The docs are done when a fresh agent session, with no memory and only the repo, follows the method on its own. The
test re-enacts past increments, as H3 re-enacts PRs: start from the commit before the change, hand the agent only
the problem as it was first seen, and watch what it does.

| Task | Starting point | The behavior that must show |
|---|---|---|
| The TS wrapper whose options come through a local (F1.14 increment 12) | the parent of `dfbc8d7` | a fixture that fails first; the corpus against a baseline; the 9 changed mattermost calls judged at the source |
| A route that exists only in a spec | an expected-list case under H2-D15 | the list corrected with evidence, in its own commit, without touching the extractor |
| An H5 refactor step (the unit tests, then the cursor walk) | the commit before H5's step 2 | `0 repo(s) differ`, the time measured alone, one cause per commit |
| A tempting hold-out miss | a task framed around a hold-out repo | it refuses to write a rule for it, and says why |
| A performance claim | "make the extraction faster" | medians of repeated runs alone, with the range, before and after |

Each task runs at least twice, because one run of a model proves little. A person scores the transcripts against
the behaviors; an LLM does not judge its own result (H3's rule). The docs are revised until every task shows its
behaviors in both runs.

## Order

1. **Gather the method into its parts** (the table above) from the decisions, the guide, the corpus report, H5, H6
   and the golden questions. Each part gets one home in the new docs, and the others point to it.
2. **The decisions** H4.1-D1…D6 with the author.
3. **Write what does not depend on the code's structure**, which H5 and H6 are changing: `CONTRIBUTING.md`, the
   explanation page, the PR and issue templates, the "Contributing" section of `AGENTS.md`, the playbooks for the
   corpus, the expected lists, the hold-out and refactoring.
4. **The CI checks** decided in step 2.
5. **After H5's step 6 and H6's ADRs:** the playbooks that describe code, such as teaching the extractor a pattern
   (a recognizer and the YAML catalog), adding a language, and the pipeline. They come from H4's phase 0b, the guide
   rewritten in English.
6. **The acceptance test**, then the revisions until it passes.

The parts written in step 3 move with the indexer to its own repo in P2 (H4-D9), so they are written with paths
relative to the indexer, and the aidd-stack keeps a short `CONTRIBUTING.md` that points there.

## Pitfalls

- **The docs become a second source of truth.** A rule written in two places drifts. Each part of the method lives
  in one page; the others link to it.
- **A playbook that names a command that changed.** The playbooks are run, not just read, in the acceptance test,
  and the CI path check catches a renamed file.
- **Too much at once.** An agent that reads 20 pages before a one-line fix skims all of them. `AGENTS.md` and
  `CONTRIBUTING.md` say which page a contribution type needs, and nothing more.
- **Writing the code playbooks before H5 and H6 land.** They would describe functions that are about to move.
- **Numbers in the docs that age.** The docs link to the corpus report for numbers, with the baseline's name; the
  explanation page tells history with dates, so it does not age.

## Constraints and conventions

- Everything in the repo is in English (H4-D1); translations follow H4-D3's tiers.
- No real tenant or private project names; public repos may be named.
- One-line conventional commits, with no body and no attribution.
- The working docs' paths do not change (H4's rule).
